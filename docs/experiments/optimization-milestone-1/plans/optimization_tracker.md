# PIGEAN optimization and convergence tracker

Updated 2026-10-12. T = T2D; N = NAFLD. Speedups are T / N, relative to the preceding retained optimization (incremental) and legacy (cumulative). Rows 1–8 record single-seed, four-outer-update inference screens with original inner controls; the separate milestone paragraph records the completed 500-update T2D comparison; rows 7–8 additionally separate compiler preparation from warmed inference; they exclude input/output and do not establish full-run speed or convergence. Each row uses its own measured controls; do not multiply ratios from different dates. Agreement covers priors and `beta_uncorrected`, including top-200 and internal iteration arrays. Unmeasured means no result, not no benefit.

The original optimization-only shortlist has completed its initial evaluation: eight local opt-in implementations, with per-chain inflation threading rejected during item 8 and independent prefilter threading retained. Their row-level evidence is preliminary; the cumulative T2D result has now been accepted by the user as the first optimization milestone, with legacy still the default. Each item retains its evidence and limitations. Combined and convergence candidates are deferred research choices, not approved production fixes. Preserve flags, defaults, independent fPS/variance branches, and atomic dependent optimization branches.


Memory figures distinguish retained cache payload from total process peak RSS (resident memory). Rows 4–8 have paired process peak-RSS measurements through inference, including imports and fixture loading; these do not isolate the allocations responsible for a difference. Row 5 also has allocation tracing, which measures tracked allocations rather than all native/resident memory and adds overhead. Earlier rows do not have isolated incremental peak-RSS comparisons. Memory expectations are incremental relative to the preceding implementation. Scaling columns are implementation-based expectations, not measured scaling curves. “More iterations” distinguishes outer updates from inner sweeps. At a fixed workload per update, runtime is approximately setup plus iteration count times per-update cost: recurring savings grow in seconds, while the speedup ratio tends to plateau. Retaining more draws can increase total memory regardless of the arithmetic engine.

For annotation scaling, compare similar gene counts, chain counts, sparsity, value repetition, and correlation structure. Adding annotations can also change selected supports and convergence difficulty, so annotation count alone cannot predict time to reliable results. Future performance screens should record comparable peak RSS (including workers for parallel methods), cache payload, cold/warm timing, and these workload dimensions.

CLI entries refer to the local experimental worktrees, not a released/main installation. In `worktrees/parallel-prefilter`, the eight implemented flags select cumulative engines: grouped includes sparse arithmetic, cached-grouped includes both, compact-covariance includes the first three optimizations, lean-regression includes all four preceding ones, cached-inner adds bounded inner-fit correlation-slice reuse, compiled-covariance compiles edge preparation using optional Numba, and parallel-prefilter adds two-thread linear covariance chunks. They are alternative values of one option, not flags to combine. Omitting the option selects `legacy`; explicit baseline: `--gibbs-engine legacy`. Unimplemented candidates have no assigned enabling flag or default status.
